## Задание 1. Имена, ссылки и изменяемость

### Эксперимент A. Неизменяемый объект

**Прогноз:** после `b = a` оба имени будут показывать на один объект `10` (идентификаторы совпадут). Операция `a += 1` не может изменить объект `int`, поэтому имя `a` будет связано с новым объектом `11`, а `b` останется указывать на `10`: значения и `id` у `a` изменятся, у `b` — нет.

**Фактический результат:**

```text
10 10
140255622320200 140255622320200        # id(a) == id(b)
11 10
140255622320232 140255622320200        # id(a) изменился, id(b) нет
```

Прогноз подтвердился. `int` — неизменяемый тип: у объекта нет операции «изменить себя», поэтому `a += 1` вычисляет новое значение `11` и **пересвязывает имя** `a` с новым объектом. Имя `b` никто не трогал, и оно продолжает ссылаться на исходный объект `10`. Именно поэтому изменение через `a` не отразилось на `b`.

### Эксперимент B. Изменяемый объект

**Прогноз:** `second = first` свяжет второе имя с тем же списком, поэтому `second.append(30)` изменит состояние, видимое через оба имени. После переназначения `second = [10, 20, 30]` списки будут равны по `==`, но не по `is`; дальнейшее изменение `second` не затронет `first`.

**Фактический результат:**

```text
[10, 20] [10, 20]
140255613782848 140255613782848        
[10, 20, 30] [10, 20, 30]              
140255613782848 140255613782848
after reassign eq/is: True False       
[10, 20, 30] [10, 20, 30, 40]          
```

Последовательно выполненные дополнения:

1. `second = [10, 20, 30]` — создан **новый** список с теми же элементами.
2. Сравнение: `first == second` → `True` (значения совпадают), `first is second` → `False` (объекты разные).
3. `second.append(40)` изменил только `second`; `first` остался `[10, 20, 30]`.
4. Схемы связей имён и объектов:

**До переназначения:**

```text
first  ──┐
         ├───▶ [10, 20, 30]   (один объект, один id)
second ──┘
```

**После переназначения `second = [10, 20, 30]`:**

```text
first  ─────▶ [10, 20, 30]      (объект №1)
second ─────▶ [10, 20, 30]      (объект №2, другой id, равное содержимое)
```

### Вопросы для анализа

1. **Меняет ли присваивание `second = first` сам объект?** Нет. Присваивание работает только с именем: оно связывает `second` с тем объектом, на который указывает `first`. Сам объект не меняется, копии не создаются, меняется только таблица имён (и счётчик ссылок объекта).
2. **Почему операция над неизменяемым объектом приводит к связыванию имени с другим объектом?** Потому что неизменяемый объект по определению не может поменять своё состояние. Единственный способ «получить изменённое значение» — вычислить новый объект и пересвязать с ним имя. Поэтому `a += 1` для `int` — это сокращение записи `a = a + 1`, т.е. создание нового объекта и новое связывание.
3. **Как определить, что два имени обозначают один объект?** Оператором `is` (проверка идентичности) либо сравнением `id(x) == id(y)`. Равенство `==` этого не показывает: два разных объекта могут быть равны по значению.

### Таблица сравнения способов копирования

| Операция | Новый внешний объект | Новые вложенные объекты | Изменения независимы |
|---|---|---|---|
| Присваивание | Нет | Нет | Нет (полностью общий объект) |
| Поверхностная копия | Да | Нет | Частично: добавление/удаление элементов независимо, изменение внутри вложенных объектов — общее |
| Глубокая копия | Да | Да (рекурсивно все) | Да, полностью |

### Ошибочное и правильное создание матрицы

**Прогноз:** `[[0] * 3] * 3` повторит одну и ту же строку три раза, поэтому `wrong_matrix[0][0] = 1` «заразит» все строки; генератор списка создаст три независимые строки.

**Фактический результат:**

```text
До изменения: [[0, 0, 0], [0, 0, 0], [0, 0, 0]]
После wrong_matrix[0][0] = 1: [[1, 0, 0], [1, 0, 0], [1, 0, 0]]
Все строки — один и тот же объект: True
Корректная матрица: [[1, 0, 0], [0, 0, 0], [0, 0, 0]]
Строки независимы: True
```

Объяснение через идентичность: оператор `*` над списками **копирует ссылки, а не объекты**. `[...] * 3` помещает три ссылки на один и тот же список `[...]`. Списковое включение `[[0] * 3 for _ in range(3)]` выполняет тело `[0] * 3` трижды, создавая три независимых объекта.

### Вопросы для анализа

1. **Чем поверхностная копия отличается от глубокой?** Поверхностная копия создаёт новый внешний контейнер, но заполняет его ссылками на те же вложенные объекты. Глубокая копия рекурсивно копирует всё достижимое поддерево объектов: не остаётся ни одного общего вложенного объекта (кроме безопасно разделяемых неизменяемых значений, для которых вопрос общности не имеет практического значения).
2. **Почему глубокое копирование не следует применять автоматически ко всем объектам?** Во-первых, оно дорогое: рекурсивный обход и создание копий каждого объекта тратит время и память. Во-вторых, оно часто избыточно: если вложенные объекты неизменяемы или их совместное использование задумано намеренно (например, общий кэш), глубокая копия нарушит смысл программы. Наконец, для очень больших или связанных структур (графы, объекты с побочными ресурсами) слепое копирование может скопировать гораздо больше, чем предполагалось.
3. **В каких случаях достаточно поверхностной копии?** Когда структура плоская (список чисел, словарь с неизменяемыми значениями), а также когда нужно защитить только внешний контейнер от добавления/удаления элементов, а вложенные объекты либо неизменяемы, либо осознанно должны оставаться общими.

## Задание 3. Подсчёт ссылок и время жизни объекта

### Изменение счётчика ссылок

**Прогноз:** каждое новое связывание увеличит счётчик на 1; `del alias` уменьшит на 1; `container.clear()` уберёт ещё одну ссылку. Абсолютные значения будут на 1 больше «логических» из-за временной ссылки в `getrefcount()`.

**Фактический результат:**

```text
После создания: 2
После создания alias: 3
После помещения в контейнер: 4
После del alias: 3
После очистки контейнера: 2
```

Прогноз подтвердился. Разбор:

- **Почему `sys.getrefcount()` показывает на одну ссылку больше.** Чтобы вызвать `sys.getrefcount(data)`, ссылку на объект требуется передать в функцию как аргумент — это создаёт временную ссылку на время вызова. Поэтому реальный счётчик в момент «После создания» равен 1 (имя `data`), а функция печатает 2.
- **Что увеличивает счётчик:** связывание имени с объектом (`alias = data`), помещение объекта в контейнер (`container = [data]`), передача в функции, захват в замыкания и т.д.
- **Что уменьшает счётчик:** `del alias` (удаление имени), переназначение имени на другой объект, удаление элемента из контейнера / его очистка (`container.clear()`), выход из области видимости локальных имён.
- **Почему `del alias` удаляет имя, а не объект.** `del` убирает запись из таблицы имён и уменьшает счётчик ссылок объекта на 1. Если у объекта остались другие ссылки (у нас — имя `data` и элемент в `container`), объект продолжает жить. Уничтожение объекта — отдельное событие, которое происходит лишь при обнулении счётчика.

### Слабые ссылки

**Прогноз:** пока существует сильная ссылка `record`, вызов `weak_record()` вернёт объект; после `del record` объект будет уничтожен (других сильных ссылок нет), и слабая ссылка вернёт `None`.

**Фактический результат:**

```text
<__main__.Record object at 0x000001FBC93B9160>
None
```

Прогноз подтвердился. Слабая ссылка не увеличивает счётчик ссылок объекта, поэтому она не продлевает его время жизни: механизм подсчёта ссылок волен уничтожить объект, как только исчезнет последняя *сильная* ссылка. Слабая ссылка лишь «наблюдает» и после уничтожения объекта сообщает `None`.

**Где слабые ссылки полезны (найденный пример):** кэш объектов, который не должен мешать их удалению. Например, библиотека кэширует загруженные из базы записи по первичному ключу, чтобы повторные запросы возвращали тот же объект. Если кэш держит сильные ссылки, записи будут жить вечно и заполонят память; со слабыми ссылками кэш сам уменьшается, когда приложение перестаёт пользоваться записью, при этом пока запись жива — повторные обращения мгновенно отдают тот же самый объект. Тот же приём применяется для сопоставления «объект → дополнительные данные» без утечек (WeakKeyDictionary) и в системах с подписчиками.

### Практическая задача (слабый реестр)

```python
class Record:
    def __init__(self, name):
        self.name = name
    def __repr__(self):
        return f"Record({self.name!r})"


registry = weakref.WeakValueDictionary()
r1 = Record("Potter")
r2 = Record("Granger")
temp = Record("Weasley")
registry["Potter"] = r1
registry["Granger"] = r2
registry["Weasley"] = temp
print("Реестр сразу после создания:", list(registry.items()))

del temp
print("\nПосле удаления временной ссылки temp (Weasley):")
print("Реестр:", list(registry.items())) 

del r2
print("\nПосле удаления сильной ссылки r2 (Granger):")
print("Реестр:", list(registry.items())) 

print("\nr1 жив благодаря сильной ссылке:", registry.get("Potter"))
```

**Фактический результат:**

```text
Реестр сразу после создания: [('Potter', Record('Potter')), ('Granger', Record('Granger')), ('Weasley', Record('Weasley'))]

После удаления временной ссылки temp (Weasley):
Реестр: [('Potter', Record('Potter')), ('Granger', Record('Granger'))]

После удаления сильной ссылки r2 (Granger):
Реестр: [('Potter', Record('Potter'))]

r1 жив благодаря сильной ссылке: Record('Potter')
```

Эксперимент на практике показал главное свойство: **слабый реестр не управляет временем жизни зарегистрированных объектов**. Как только удалена последняя сильная ссылка (`del temp`, затем `del r2`), объект уничтожается, а соответствующая запись автоматически исчезает из `WeakValueDictionary` — никакого ручного удаления из реестра не потребовалось.

### Вопросы для анализа

1. **При каком условии подсчёт ссылок позволяет освободить объект?** Когда счётчик ссылок объекта падает до нуля — т.е. на объект больше не указывает ни одно имя, контейнер или другой объект. Дальше объект обязан быть достижимым: нулевой счётчик = недостижимость. Но обратное неверно: ненулевой счётчик ещё не гарантирует достижимость, поэтому одного подсчёта ссылок недостаточно.
2. **Всегда ли освобождение Python-объекта означает немедленный возврат памяти операционной системе?** Нет. Память сначала возвращается во внутренние пулы и арену-менеджеры CPython, которые переиспользуют её внутри процесса. ОС память обычно возвращается лишь когда освобождается целый блок (арена) или при работе с очень большими объектами. Поэтому «объект удалён» и «RSS процесса уменьшился» — не одно и то же.
3. **Чем сильная ссылка отличается от слабой?** Сильная ссылка участвует в подсчёте ссылок и поэтому удерживает объект: пока есть хотя бы одна сильная ссылка, объект гарантированно жив. Слабая ссылка на счётчик не влияет: она позволяет обратиться к объекту, пока он жив, но не мешает его уничтожению; после уничтожения она «обнуляется» (возвращает `None`).

```text
Цикл из first/second больше не достижим ни по одному имени,
но до вызова gc.collect() подсчёт ссылок не мог его освободить,
т.к. оба списка (id=1299228520384, id=1299228636608) ссылались друг на друга.
```

- Состояние автоматического сборщика: `gc.isenabled()` → `True`.
- Пороги поколений: `(2000, 10, 10)` — сборка поколения 0 запускается, когда разница «создано контейнеров − удалено контейнеров» превысит 700… в данной сборке 2000; после 10 сборок поколения 0 проверяется поколение 1, после 10 сборок поколения 1 — поколение 2 (конкретные числа зависят от версии CPython).
- Статистика поколений: три словаря по поколениям 0/1/2 с полями `collections`, `collected`, `uncollectable`.

**Почему одного подсчёта ссылок недостаточно.** После удаления внешних имён у каждого списка остаётся счётчик 1 — ссылка из «соседа» по циклу. С точки зрения подсчёта ссылок оба объекта «кто-то использует», хотя из программы к ним пути уже нет. Подсчёт ссылок умеет реагировать только на обнуление счётчика, а в цикле счётчики не обнуляются никогда. Нужен отдельный анализ достижимости: циклический сборщик находит изолированные островки объектов, ссылающихся только друг на друга, и удаляет их целиком.

**Назначение поколений.** Молодые объекты умирают чаще всего (временные списки, промежуточные структуры), а пережившие несколько сборок — скорее долгожители. Поэтому сборщик делит отслеживаемые объекты на поколения: молодое проверяет часто и быстро, старые — всё реже. Это экономит общее время сборки, не жертвуя сбором мусора: цена каждой сборки молодого поколения мала, а редкие полные сборки добирают оставшееся.

### Эксперимент с отключённым сборщиком

**Прогноз:** при отключённом `gc` созданные циклы (списки, ссылающиеся сами на себя) после удаления внешних ссылок никуда не денутся автоматически; ручной `gc.collect()` их соберёт и вернёт их число.

```python
gc.disable()
print("Автосборка отключена:", not gc.isenabled())

garbage_ids = []
for _ in range(3):
    a, b = [], []
    a.append(b)
    b.append(a)
    garbage_ids.append((id(a), id(b)))
    del a, b

collected = gc.collect()
print(f"Ручной gc.collect() собрал: {collected} объектов")
``` 

**Фактический результат:**

```text
Автосборка отключена: True
Ручной gc.collect() собрал: 6 объектов
```

Все три циклических списка собраны вручную. Автоматическая сборка после эксперимента восстановлена (`gc.isenabled()` → `True`). Тонкость, обнаруженная опытным путём: если не удалить переменную цикла `x` (`del junk` без `del x`), собирается только 2 объекта из трёх — имя `x` продолжает держать последний список сильной ссылкой. Важно помнить, что `del` должен убрать **все** внешние ссылки, иначе цикл остаётся достижимым и сборщик его не трогает.

### Практическая задача (модель графа)

**Схема графа:**

```text
node_a ──links──▶ node_b ──links──▶ node_c ──links──▶ node_a
node_d ──links──▶ ∅                              
```

Соответствие схемы коду — каждое ребро реализовано одним `append`:

```python
gc.enable()
print("Автосборка снова включена:", gc.isenabled())

node_a = {"name": "Американец","links": []}
node_b = {"name": "Немец","links": []}
node_c = {"name": "Француз","links": []}
independent = {"name": "Русский (независимый)", "links": []}

node_a["links"].append(node_b)
node_b["links"].append(node_c)
node_c["links"].append(node_a)

print("\nСвязи в графе")
for n in node_a,node_b,node_c,independent:
    targets = [t["name"] for t in n["links"]]
    print(f"{n['name']} -> {targets if targets else '[]'}")

before = gc.collect()
print(f"\nСобрано мусора до удаления графа: {before}")

del node_a, node_b, node_c
after = gc.collect()
print(f"Собрано мусора после удаления графа: {after}")

print("\nНезависимый узел по-прежнему доступен:", independent)
assert independent["name"] == "Русский (независимый)"
```

**Фактический результат:**

```text
Связи в графе
Американец -> ['Немец']
Немец -> ['Француз']
Француз -> ['Американец']
Русский (независимый) -> []

Собрано мусора до удаления графа: 0
Собрано мусора после удаления графа: 6

Независимый узел по-прежнему доступен: {'name': 'Русский (независимый)', 'links': []}
```

Сравнение: до создания графа (после предварительной `gc.collect()`) сборка ничего не находила, а после `del node_a, node_b, node_c` ручная сборка собрала **6 объектов**: 3 словаря-узла и 3 связи. Независимый узел `independent` остался доступен — он не входил в цикл и удерживался своим именем.

### Вопросы для анализа

1. **Как возникает циклическая ссылка?** Когда цепочка ссылок объектов замыкается в кольцо: объект A (прямо или через другие объекты) ссылается сам на себя. Типичные источники: взаимные ссылки «родитель <=> потомок», «объект <=> его обработчик», узлы графа или двусвязного списка, а также самоссылка (`x.append(x)`). Циклы возможны только у изменяемых контейнерных объектов — неизменяемый объект не может начать ссылаться на что-то после создания.
2. **Почему объект с ненулевым счётчиком ссылок иногда может быть недостижим из программы?** Потому что счётчик отражает лишь количество входящих ссылок, но не то, *откуда* они идут. Если все ссылки на объект приходят из других объектов того же цикла, счётчик ненулевой, а ни одна цепочка от корневых имён программы (локальные переменные, модули и т.д.) до объекта не ведёт. Так называемый «мусорный остров»: объекты ссылаются друг на друга, но программе они уже недоступны.
3. **Зачем сборщик мусора разделяет отслеживаемые объекты по поколениям?** Чтобы сократить суммарные затраты на поиск циклов, опираясь на эмпирический факт: большинство объектов умирает молодыми. Молодые объекты проверяются часто (и каждая проверка дешёвая — список короткий), пережившие несколько сборок «повышаются» в более старое поколение и проверяются редко. Отдельно стоит отметить: поколения отслеживают только контейнерные объекты, способные участвовать в циклах (списки, словари, экземпляры классов); атомарные объекты вроде `int` и `str` сборщиком не отслеживаются.

## Задание 5. Исследование потребления памяти

### Часть 1. Размер отдельных объектов

**Прогноз:** список из десяти целых будет заметно больше пустого ; кортеж чуть меньше списка (нет резерва роста); односимвольная ASCII-строка дешёвая; `int` и `None` имеют фиксированный небольшой размер.

**Фактический результат (байты):**
```text
пустой список: 56 байт
список из 10 int: 136 байт
кортеж из 10 int: 128 байт
строка из 10 символов: 51 байт
целое число: 28 байт
None: 16 байт
```
Прогноз подтвердился: пустой список 56 байт (заголовок + поле выделенной ёмкости), список из 10 элементов — на 80 байт больше (10 ссылок × 8 байт), кортеж с теми же элементами меньше списка, потому что не хранит запас под будущие добавления.

**Почему размер контейнера не включает полный размер его содержимого.** `sys.getsizeof()` по умолчанию возвращает *поверхностный* размер: только память самого объекта-контейнера (заголовок + массив ссылок). Сами элементы — отдельные объекты со своими счётчиками и памятью; контейнер хранит на них лишь указатели. Поэтому список из 10 чисел «весит» 136 байт, хотя реальная суммарная память больше на размеры самих `int`. Это же объясняет, почему десять ссылок на один и тот же большой объект стоят столько же, сколько ссылки на десять разных.

### Часть 2. Рост списка

**Прогноз:** размер будет меняться ступенями, а не на каждый `append()` — список выделяет память блоками с запасом.

**Фактический результат** (выводились только моменты изменения размера):

```text
len=0 size=56 байт (начальное выделение)
len=1 size=88 байт (выделение изменилось)
len=5 size=120 байт (выделение изменилось)
len=9 size=184 байт (выделение изменилось)
len=17 size=248 байт (выделение изменилось)
len=25 size=312 байт (выделение изменилось)
len=33 size=376 байт (выделение изменилось)
len=41 size=472 байт (выделение изменилось)
len=53 size=568 байт (выделение изменилось)
len=65 size=664 байт (выделение изменилось)
len=77 size=792 байт (выделение изменилось)
len=93 size=920 байт (выделение изменилось)
```

Ответы по наблюдениям:

- **Увеличивается ли размер после каждого `append()`?** Нет. Из 100 добавлений лишь 11 привели к перевыделению памяти; остальные помещались в ранее зарезервированное место.
- **Почему список резервирует место с запасом?** Перевыделение требует заказать новый блок и скопировать все ссылки. Если бы память росла ровно на элемент, добавление N элементов стоило бы O(N²) копирований. Резервирование даёт амортизированную стоимость `append()` ≈ O(1). Цена — умеренный избыток памяти.
- **Чем длина отличается от выделенной памяти?** `len(lst)` — число занятых слотов (логический размер). Выделенная память определяется ёмкостью — числом слотов, под которые реально выделен массив; ёмкость ≥ длины, избыток — как раз резерв роста. `getsizeof` показывает память под всю ёмкость, а не под длину.

### Часть 3. Измерение через `tracemalloc`

**Прогноз:** `list(range(100_000))` выделит заметный объём (массив из 100 000 ссылок плюс сами объекты `int`), а `range(100_000)` — всего десятки байт под объект-диапазон, хранящий только `start`, `stop`, `step`.

**Фактический результат:**

list(range(100_000)): текущее=3898.383 КБ, пиковое=3898.383 КБ, size=800056 байт
range(100_000): текущее=0.078 КБ, пиковое=0.078 КБ, size=48 

**Вывод.** Материализованная последовательность (`list`) хранит *каждое* значение физически: массив из 100 000 ссылок (~781 KiB) плюс ~100 000 отдельных объектов `int` по 28 байт — итого около 3,8 MiB. Объект `range` хранит только *правило* получения значений (три числа и счётчик итерации), поэтому стоит 48 байт независимо от диапазона.

### Итоговый анализ: как уменьшить лишнее потребление памяти

1. **Использовать ленивые последовательности и итераторы вместо материализации.** `range`, генераторные выражения, `map`, потоковая обработка файлов. Основание: эксперимент 5.3 — замена `list(range(100_000))` на `range` уменьшила пиковое потребление в ~50 000 раз без изменения логики перебора.
2. **Выбирать компактные контейнеры под задачу.** Кортеж вместо списка там, где набор не редактируется (120 байт против 136 и без резерва роста); для больших однородных числовых массивов — `array.array` или `numpy`, хранящие значения «в разворот», без объекта на каждый элемент; избегать лишних вложенных копий. Основание: эксперименты 5.1 (разница стоимости контейнеров) и 5.2 (резерв роста списка — налог на изменяемость).
3. **Не удерживать объекты дольше нужного и следить за циклами.** Удалять ненужные ссылки/имена крупных структур, разрывать циклические ссылки, использовать слабые ссылки для кэшей и реестров (`weakref.WeakValueDictionary`), а не «вечные» сильные словари. Основание: задания 3 и 4 — слабый реестр освобождал записи автоматически, а цикл A→B→C→A без `gc` жил бы до полной сборки.

## Итоговый вывод

2. **Самые опасные ошибки при работе с изменяемыми объектами:**
   - *Незаметное совместное владение:* `second = first`, передача списка в функцию, изменяемое значение по умолчанию в сигнатуре — один и тот же объект меняется из разных мест программы, и побочный эффект проявляется вдали от причины.
